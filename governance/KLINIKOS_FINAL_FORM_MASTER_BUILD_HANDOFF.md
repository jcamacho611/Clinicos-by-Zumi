## 0. Mission

Build Klinikos into a real production-grade healthcare operating network, not a mockup, feature collage or founder demo.

Klinikos should progressively become the primary environment through which healthcare organizations coordinate care, operations, revenue, capacity, workforce, education, relationships, payments, evidence and governed intelligence.

Permanent laws:

> **The complexity belongs to Klinikos, not to the person using Klinikos.**

> **What needs to happen next?**

> **Own the workflow first. Abstract the vendor. Internalize only when customer value, margin, control, reliability and regulatory feasibility justify it.**

## 1. Agent authority

Implementation agents have broad authority to add, remove, combine, rename, refactor, harden, generalize, move, hide, automate or replace product implementation when the result is demonstrably better.

That authority does not permit agents to:

- destroy authoritative data casually
- create parallel clinical, financial, identity or entitlement authorities
- weaken authorization, tenant isolation, clinical safety, audit or privacy
- fabricate integrations, customers, revenue, payments, certifications, licenses or clinical facts
- silently delete direct founder/professional/customer requirements
- expose proprietary prompts, ranking, security heuristics, margins, secrets or unnecessary sensitive data to the browser
- call an adapter a live production integration
- call a redirect a payment
- let AI become final authority for diagnosis, prescription, clinical signature, licensure, consent, credential verification or unauthorized financial settlement

## 2. Truth classes

Always label important statements as one of:

- **CURRENT FACT**: repository/runtime/provider/contract evidence proves it.
- **PROPOSED**: architecture, pricing, strategy or opportunity not yet enacted.
- **EXECUTED**: implemented, activated, signed, paid, connected or otherwise made effective.

A strategy document never makes a proposal executed.

## 4. Plain-English frontend constitution

Every user-facing state communicates in this order:

1. what is happening
2. why it matters
3. what the user can do
4. what happens next
5. professional detail only when useful

Examples:

- `AUTHORIZATION_REQUIRED` → **Insurance approval is still needed.**
- `CLAIM_REJECTION` → **This claim needs attention before it can continue.**
- `REMITTANCE_EXCEPTION` → **This payment still needs review.**
- `RESULT_REVIEW_PENDING` → **A result is ready for provider review.**
- `REFERRAL_OPEN` → **This referral still needs follow-up.**

Do not leak backend vocabulary into UX because it is convenient.

## 14. Care OS

Care OS progressively supports patient chart, Current Visit, Clinical Change, BodyMap, scheduling, staff handoff, referrals, orders/results, documents/forms, telemedicine, procedures, signatures/addenda, specialty configuration and No-Fault/Workers' Comp.

### Current Visit

Preserve the existing encounter authority and sequence:

`PATIENT SNAPSHOT → WHAT CHANGED → STAFF HANDOFF → TODAY → CLINICAL → ASSESSMENT & PLAN → ORDERS & RESULTS → DOCUMENTATION & CODING → CLOSE VISIT`

Source-locked professional requirements include demographics, identity/photo context, emergency/next-of-kin, coverage/case context, consent/authorization states, advance-care-planning/immunization context where relevant, histories, medications, allergies, problems, chief complaint, HPI, ROS, vitals, physical exam, assessment/plan, procedures, injections, shockwave/Botox where relevant, labs, imaging, consultation reports, EMG results/impressions, referrals, codes/modifiers, AI dictation, telemedicine, staff handoff, longitudinal BodyMap, functional change, case context, signature/addenda and billing readiness.

### Clinical Change

Structured evidence should support `INITIAL → PREVIOUS → TODAY` for symptoms, pain, body region, laterality, function, ADLs, ROM, exam findings, work status, treatment, medication, procedures, labs, imaging and unresolved/new findings.

AI explains evidence; it does not invent change.

### Specialty Packs

Specialty variation belongs primarily in configuration and reusable clinical components, not separate code forks.

## 16. Revenue Integrity OS

Core chain:

`PERFORMED → DOCUMENTED → CODE SUPPORTED → CHARGE EXPECTED → CHARGE PRESENT → CLAIM READY → CLAIM SENT → ACCEPTED → ADJUDICATED → PAID → RECONCILED`

Broken transitions create review work.

Revenue language must distinguish potential, estimated, verified, submitted, paid and reconciled.

## 17. Insurance and prior authorization

Eligibility flow:

`PATIENT + COVERAGE → PAYER IDENTIFICATION → ELIGIBILITY → BENEFITS/LIMITS → REFERRAL/AUTHORIZATION REQUIREMENTS → READY / NEEDS ACTION`

Authorization flow:

`SERVICE + PATIENT + PAYER + PLAN + EVIDENCE → REQUEST → SUBMISSION → ACKNOWLEDGMENT → STATUS → APPROVAL/DENIAL → EXPIRATION → FOLLOW-UP/APPEAL`

Zumi may identify, gather, prepare, transmit through approved rails, monitor and escalate. Professional authority remains where required.

## 18. Coding Intelligence

Support ICD-10-CM, CPT, HCPCS, modifiers, effective dates, documentation support, diagnosis/procedure relationships, medical-necessity evidence and payer/case context.

Frontend:

- Suggested
- Why it may fit
- Supporting evidence
- What's missing
- Human decision

AI cannot invent diagnoses, laterality or documentation to justify reimbursement.

## 19. Claims / clearinghouse

Klinikos owns canonical claim state while clearinghouses/payers remain external rails until/unless later internalization is justified.

Architecture should support applicable X12 transaction families through adapters, idempotency, acknowledgment, retry, reconciliation and truthful lifecycle state.

The clinic should operate Klinikos rather than manually operate a clearinghouse portal whenever connected workflows allow it.

## 21. Zumi Runtime

One user-facing Zumi, many governed internal capabilities.

Runtime components include intent routing, authorized context assembly, policy, tool registry, orchestration, workflow planning, evidence retrieval, memory, model routing, human approval, cost governance, evaluations and AI audit.

Autonomy:

- L0 Observe
- L1 Recommend
- L2 Prepare
- L3 Execute after authorized approval
- L4 Explicitly pre-authorized low-risk deterministic autopilot
- L5 Prohibited autonomy

L5 includes diagnosis, prescribing, clinical signature, licensure/credential authority, patient consent, high-risk clinical decision and unauthorized financial settlement.

### Morning autopilot

Where authorized, inspect appointments, intake, forms, coverage, authorization, staff, rooms/resources, telehealth readiness, results, referrals, documentation blockers and integration health.

### End-of-day autopilot

Inspect unsigned notes, unresolved results/orders/referrals, coding/revenue blockers, callbacks, authorizations, reconciliation and next-day readiness.

## 22. Grid Exchange

Public grammar: **I NEED / I HAVE**.

Potential resource classes include professionals, work, shifts, temporary coverage, rooms/chairs/offices, equipment, business services, education/preceptors/placements, professional capacity and diagnostic capacity.

Transaction path:

`DEMAND + RESOURCE + TIME + LOCATION + REQUIREMENTS + ELIGIBILITY → CANDIDATES → RANKING → OFFER → AGREEMENT → RESERVATION → FULFILLMENT → EVIDENCE → FINANCIAL CONSEQUENCE → RELATIONSHIP`

Eligibility precedes ranking. Payment never creates eligibility.

Liquidity is measured by `RESOURCE TYPE × GEOGRAPHY × TIME × ELIGIBILITY CLASS`.
