# KLINIKOS MULTI-AGENT EXECUTION CONTROL

Version: `2026-08-27.1`
Status: `ACTIVE EXECUTION CONTROL - SUBORDINATE TO KLINIKOS MASTER CANON`

This document coordinates humans and implementation agents working on Klinikos. It does not redefine product truth. `docs/KLINIKOS_MASTER_CANON.md` remains the sole product/architecture/business/experience authority.

## 1. Why this exists

Klinikos is too broad for independent agents to safely optimize isolated files without coordination. The failure mode is predictable: one agent rebuilds onboarding, another revives an old role model, another creates a second Zumi path, another treats Grid as a page instead of a spatial exchange, and documentation becomes multiple competing snapshots.

The operating rule is therefore:

> **ONE KLINIKOS, MANY EXECUTION LANES, ONE CURRENT MAIN, ONE MASTER CANON.**

No agent owns a separate version of Klinikos.

## 7. Concurrency law

Before writing, every agent must inspect current `main` and open PRs touching the same domain/files.

If another active branch owns overlapping implementation:

1. do not overwrite it;
2. determine whether the new task is additive, dependent, superseding, or conflicting;
3. choose one of: stack intentionally, work in non-overlapping files, wait for merge, or re-anchor the older work;
4. record the relationship in the handoff;
5. never mass-merge stale branches to recover one useful idea.

One active owner per consequential implementation slice is preferred. Multiple agents may collaborate only when file/authority boundaries are explicit.

## 8. Mandatory handoff contract

Every material agent handoff must contain:

1. **Objective** - what outcome the tranche is responsible for.
2. **Canon basis** - exact Master Canon sections/decision IDs governing it.
3. **Repository** - `jcamacho611/Clinicos-by-Zumi`.
4. **Base** - exact base branch/SHA inspected before work.
5. **Head** - exact branch/SHA after work.
6. **PR** - number/state/draft status if one exists.
7. **Files changed** - exact paths and why.
8. **What is actually built** - factual behavior only.
9. **What remains unbuilt/external** - explicit gaps.
10. **Authority boundaries** - what the change cannot authorize or prove.
11. **Security/confidentiality review** - browser/server boundary and disclosure consequences.
12. **Data/migration impact** - schema/migrations/backfill/rehearsal state.
13. **Tests/verification executed** - commands/runs and exact results.
14. **Browser/mobile/accessibility evidence** - where user-facing.
15. **External dependencies** - vendor/legal/contract/credential/deployment blockers.
16. **Concurrency/overlap** - other PRs/branches that must be reconciled.
17. **Next dependency-safe action** - one clear next tranche.
18. **No-claims list** - important things that must not be represented as live/verified/approved.

A handoff that only says "done" or "continue" is invalid.

## 11. Merge law

A feature is not finished because a branch exists.

Default:

`FETCH → COMPARE → INSPECT → PRESERVE → RE-ANCHOR → TEST → REVIEW → MERGE`.

Before merge:

- reconcile latest `main`;
- resolve overlapping active PRs;
- run applicable schema/migration/type/lint/test/security/build/start gates;
- run browser/mobile/accessibility checks for user-facing work;
- verify confidentiality/client-boundary consequences;
- verify PR description matches exact head;
- keep external blockers explicit;
- merge only a head whose evidence supports the claim being made.
