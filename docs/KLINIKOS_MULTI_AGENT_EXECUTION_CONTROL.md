# KLINIKOS MULTI-AGENT EXECUTION CONTROL

**Status:** ACTIVE EXECUTION CONTROL  
**Authority class:** SUBORDINATE_EXECUTION_CONTROL  
**May override Master Canon:** No  
**Governing product authority:** `docs/KLINIKOS_MASTER_CANON.md`  
**Canonical engineering contract:** `docs/superpowers/specs/2026-08-29-klinikos-master-engineering-blueprint.md`

## 1. Purpose

Klinikos may be worked on by multiple agents and humans at the same time. This file prevents duplicate implementation, stale-snapshot resurrection, cross-branch overwrites, and authority drift.

Permanent law:

> **ONE KLINIKOS. MANY EXECUTION LANES. ONE ACTIVE OWNER PER CONSEQUENTIAL SLICE.**

No agent may create a parallel product doctrine, parallel identity system, parallel Grid, parallel Zumi, parallel Financial OS, parallel patient model, parallel clinical record, parallel entitlement system, or parallel execution truth merely because another branch is inconvenient.

## 2. Authority hierarchy every agent must follow

1. `docs/KLINIKOS_MASTER_CANON.md` — what Klinikos is and should become.
2. `docs/superpowers/specs/2026-08-29-klinikos-master-engineering-blueprint.md` — engineering-buildable implementation contract generated by the Canon.
3. Current verified implementation — code, schema, migrations, tests, exact-head CI, deployment/runtime evidence, verified external connections — what exists today.
4. This file and agent bootstrap files — ownership/sequencing/handoff rules.
5. Specialist references and evidence registers — detail and proof only.
6. Historical/retired artifacts — provenance only.

Conflict handling:

- product-direction conflict → Master Canon wins;
- implementation-status conflict → current verified implementation wins;
- execution-ownership conflict → this control plane decides ownership, then the orchestrator resolves overlap;
- do not merge a conflict silently.

## 4. Work assignment law

Before a consequential task begins, record or determine:

- owning agent;
- branch/PR;
- exact base SHA;
- files/domain expected to change;
- upstream dependencies;
- downstream consumers;
- tests/verification required;
- whether another branch currently owns overlapping files.

Prefer one active owner per consequential file/domain slice.

If two agents need the same area:

1. identify the authoritative upstream contract;
2. assign one agent to produce that contract first;
3. hand it off;
4. second agent consumes it afterward;
5. never allow both agents to independently invent the interface.

## 5. Standard sequencing

Default high-risk cross-stack sequence:

`CANON / CONTRACT → SERVER DOMAIN → SAFE DTO / API → FRONTEND EXPERIENCE → BROWSER QA → FULL VERIFICATION → COMMERCIAL/OPERATING HANDOFF`

For a UX-discovered backend requirement:

`CLAUDE DISCOVERY → SERVER CONTRACT HANDOFF → CODEX IMPLEMENTS/TRUTHS → CLAUDE REALIZES EXPERIENCE → VERIFY`

For a commercial requirement:

`SYMPHONY EVIDENCE → ORCHESTRATOR CLASSIFIES → CANON/BLUEPRINT CHECK → OWNER ASSIGNED → ENGINEERING ACCEPTS → IMPLEMENT → VERIFY → SYMPHONY MAY PROMISE/SELL ONLY VERIFIED OR APPROVED FUTURE SCOPE`

For a Symphony-routed company task:

`SYMPHONY INTAKE / EVIDENCE → ORCHESTRATOR / CONTROL-PLANE OWNERSHIP CHECK → ACTIVE OWNER OR NEW OWNER → EXECUTE IN OWNED LANE → VERIFY → HANDOFF → SYMPHONY UPDATES STATUS / NEXT ACTION`.

## 7. Branch and PR law

- Never mass-merge stale branches.
- Fetch/re-read branch heads immediately before writes and integration.
- Reconcile current `main` before final merge.
- Preserve unrelated parallel-agent commits.
- If a branch moved during work, re-read overlapping files before pushing another change.
- A green result belongs only to the exact SHA tested.
- Draft PRs remain unshipped work until merged.
- Documentation claims must distinguish branch truth from `main` truth.

unless the exact disclosure passes recipient, purpose, classification, minimum-necessary, contractual, security, and governing-approval gates.
