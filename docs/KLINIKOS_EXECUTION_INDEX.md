# 4. Implementation states

Use these words precisely:

- `DESIGNED` — architecture/spec exists.
- `PLANNED` — implementation plan exists.
- `RED` — failing test/evidence intentionally proves missing behavior.
- `CODED` — implementation exists on a branch.
- `TESTED` — focused verification passed.
- `CI_GREEN` — exact candidate head passed required CI.
- `MERGE_READY` — review/concurrency/required gates are satisfied.
- `MERGED` — GitHub proves integration into `main`.
- `DEPLOYED` — deployment provider proves candidate/main SHA was deployed.
- `PRODUCTION_VERIFIED` — runtime/browser/integration evidence proves the required production journey.
- `BLOCKED_EXTERNAL` — a real external dependency is unresolved; independent work should still continue.
- `HISTORICAL` — preserved evidence, not current implementation authority.
- `RETIRED` — intentionally unavailable for new/current use.

Never collapse these states into “done.”

`VISIBLE UI → ACTION → IDENTITY/CONTEXT → INTENT → AUTHORIZATION/ELIGIBILITY → DOMAIN ENGINE → REAL DATA → PERSISTENCE/EVENT → TRUTHFUL RESULT → AUDIT/FINANCIAL STATE → NEXT ACTION`

For release claims, preserve exact evidence:

- base SHA;
- head SHA;
- migrations;
- Prisma validation/generation;
- typecheck;
- lint;
- focused + full tests as applicable;
- production build/start smoke;
- browser journeys;
- mobile 390px meaningful task;
- keyboard/screen reader semantics;
- reduced motion;
- 200% zoom;
- WebGL/degraded/Precision behavior for spatial work;
- confidentiality/security checks;
- deployment SHA and runtime verification when claiming deployment/production.

A green build is not production proof. A Stripe Product/Price is not revenue proof. An uploaded credential is not verification. A sent referral is not closure. A model output is not clinical authority.

# 10. Retirement and provenance

Historical artifacts are valuable when clearly labeled and dangerous when ambiguous.

When something is superseded:

1. identify the replacement authority;
2. classify old code/doc/PR as historical, compatibility-only, migration-only, or retired;
3. preserve immutable evidence needed for accounting, payment, legal, audit, customer history, published submissions, or incident analysis;
4. remove the old path from current user/admin/Zumi/new-sale authority;
5. add a regression search/test when the obsolete concept is high risk;
6. close or clearly disposition stale PRs only after useful work is harvested;
7. never rewrite published Git history simply to make prior decisions disappear.

# 13. Blocker rule

Preferred tool unavailable does not mean objective impossible.

Use:

`PRIMARY PATH → FALLBACK A → FALLBACK B → OPEN STANDARD / EXISTING PROVIDER → NATIVE IMPLEMENTATION → MANUAL-BUT-TRUTHFUL WORKFLOW`

Then:

`BLOCKER → ROUTE AROUND → VERIFY → CONTINUE`

Do not silently route around a blocker when doing so would spend/commit funds, enter a contract, send external communication, accept a meeting, make an attestation, weaken security/privacy, expose PHI/PII, materially change approved architecture/customer terms, create regulated authority, or fabricate evidence.

# 14. Session handoff checklist

- current `main` SHA;

- PR number/state;
- implementation state (`RED`, `CODED`, `CI_GREEN`, etc.);
- changed files;

- unresolved failures/blockers;
- overlap/concurrency discovered;
- external systems read or mutated;
- next exact task;
