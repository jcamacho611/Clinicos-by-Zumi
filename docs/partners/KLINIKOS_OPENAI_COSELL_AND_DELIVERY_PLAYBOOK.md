# KLINIKOS × OPENAI CO-SELL & DELIVERY PLAYBOOK

Version: `2026-08-27.1`  
Status: `COMMERCIAL / PARTNER EXECUTION CANON`

## 1. Goal

Turn OpenAI Partner Network membership into repeatable customer value, delivery capability and earned distribution leverage.

The objective is not to decorate Klinikos with the OpenAI name. The objective is:

`QUALIFIED CUSTOMER PROBLEM → KLINIKOS SOLUTION → APPROVED OPENAI-POWERED WORKLOAD → PRODUCTION DEPLOYMENT → MEASURED OUTCOME → PARTNER EVIDENCE → JOINT OPPORTUNITY / CO-SELL WHEN PROGRAM RULES ALLOW`.

## 2. What Klinikos sells

Klinikos sells the healthcare operating ecosystem. OpenAI powers selected Zumi intelligence workloads.

Customer value propositions remain problem-based:

- reduce workflow fragmentation;
- make unfinished work visible;
- simplify Current Visit;
- improve documentation workflow;
- surface revenue exceptions;
- connect staffing/capacity needs to Grid;
- connect education to workforce opportunity;
- provide governed AI assistance with human authority preserved.

Do not sell `GPT access` as the product.

## 3. Co-sell candidate profile

A candidate is strong when:

- organization is real and identified;
- buyer/problem owner is known;
- problem is expensive or strategically important;
- Klinikos has a bounded implementation path;
- OpenAI adds material reasoning/interaction value;
- data class is approved for the intended rail;
- success metric can be measured in 30–90 days;
- customer can provide feedback/reference if successful;
- opportunity size justifies partner involvement.

## 4. First five solution motions

### Motion 1 — Clinic operating intelligence

Buyer: clinic owner/practice manager.

Problem: fragmented staff work, missed follow-up, unclear ownership, operational overload.

Klinikos: organization map, task/workflow truth, Grid, Financial OS, Zumi.

OpenAI role: intent understanding, synthesis, explanation, drafting, next-action preparation.

Success: time-to-resolution, unresolved-work reduction, user adoption, support burden, AI task success.

### Motion 2 — Current Visit documentation assistance

Buyer: independent practice/provider organization.

Problem: provider spends too much time reconstructing visit context and documenting.

Klinikos: Current Visit, deterministic clinical facts/change, note lifecycle, coding review.

OpenAI role: evidence-linked draft/summarization after PHI gate is approved.

Success: provider documentation time, draft acceptance/edit rate, unsupported-claim rate, close-visit time.

### Motion 3 — Revenue exception intelligence

Buyer: owner/billing operations.

Problem: money stops between performed work and reconciled payment.

Klinikos: Revenue Integrity / Financial OS truth graph.

OpenAI role: explain exceptions, prioritize, prepare follow-up/documentation work.

Success: exception age, resolution rate, verified dollars advanced/recovered, staff time.

### Motion 4 — Grid workforce/capacity orchestration

Buyer: clinic/network/workforce organization.

Problem: staffing/capacity/resource needs are expressed informally and fulfilled manually.

Klinikos: I NEED / I HAVE, eligibility, matching, relationship/evidence.

OpenAI role: normalize intent, prepare structured demand/supply, explain matches.

Success: time-to-valid-demand, match rate, fulfillment rate, repeat usage.

### Motion 5 — Responsible AI workforce training

Buyer: workforce board/college/employer.

Problem: workers need practical AI literacy without unsafe or dishonest use.

Klinikos: EDU, scenarios, instructor review, evidence, workforce connection.

OpenAI role: practical exercises, feedback, simulation where approved.

Success: completion, measured skill gain, participant confidence, instructor evidence, employment/work-based-learning linkage where attributable.

## 5. Opportunity stages

### Stage 0 — Discovery

Required CRM fields:

- organization;
- contact;
- problem;
- decision maker;
- budget/contract path if known;
- desired outcome;
- data class;
- product motion;
- potential OpenAI workload;
- next action.

### Stage 1 — Klinikos qualified

Prove Klinikos can deliver the non-AI core of the workflow. Do not use OpenAI as camouflage for a missing product substrate.

### Stage 2 — AI workload qualified

Define:

- exact input data;
- exact output;
- model task;
- tools;
- human review;
- PHI/data gate;
- evaluation criteria;
- expected usage/cost.

### Stage 3 — Partner qualification

Check Partner Portal rules for whether the opportunity qualifies for registration, co-sell, referral, solution engineering or other support.

### Stage 4 — Proposal

Customer-facing proposal clearly separates:

- Klinikos responsibilities;
- customer responsibilities;
- OpenAI API dependency;
- external integrations;
- data/security assumptions;
- pricing;
- measurable acceptance.

### Stage 5 — Deployment

No fake integration. Track code SHA, environment, data class, model config, tool set, customer users, acceptance tests and known blockers.

### Stage 6 — Outcome proof

Capture before/after and customer confirmation.

### Stage 7 — Expansion / case story

Only after successful evidence. Public case story requires explicit customer and any required OpenAI approval.

## 6. Deal registration packet

If/when Partner Portal exposes deal registration, prepare:

- customer legal name;
- website/location;
- decision-maker/contact;
- opportunity stage;
- use case;
- expected OpenAI workload;
- estimated model/API consumption if required;
- expected contract value;
- target close date;
- technical architecture summary;
- security/data classification;
- implementation timeline;
- requested OpenAI assistance.

Do not fabricate fields to force qualification.

## 7. What to ask OpenAI for

According to actual current program availability, requests may include:

- partner onboarding guidance;
- certification path;
- architecture/technical enablement;
- solution engineering for a qualified opportunity;
- deal-registration/co-sell process;
- enterprise API/pricing guidance;
- healthcare/BAA process guidance;
- partner directory/market development rules;
- joint event/webinar/case-study routing;
- education/workforce contact;
- API credits only if a real benefit exists.

Ask only for benefits the current Partner Portal says exist.

## 8. Klinikos 10 and OpenAI

Klinikos 10 is the preferred initial proof cohort.

For each Founding Clinic:

1. identify the highest-value non-AI workflow problem;
2. establish deterministic Klinikos truth and workflow;
3. identify one bounded Zumi workload;
4. run synthetic/non-PHI if PHI rail is not approved;
5. measure quality, cost and operational outcome;
6. graduate only approved workloads to live sensitive data;
7. capture reference consent separately.

The ten clinics should not all receive the same AI feature. Choose the workload that solves each clinic's real problem while building reusable solution patterns.

## 9. Partner certification strategy

When PartnerU/catalog truth is known, prioritize certifications that improve delivery of Klinikos' actual product.

Preferred competency sequence:

1. OpenAI platform/API administration and security;
2. Responses/tool orchestration;
3. agent/workflow delivery if a formal track exists;
4. evaluation/safety;
5. enterprise deployment/security;
6. industry/healthcare specialization only if officially available and earned.

Do not chase certificates that do not improve customer delivery.

## 10. Co-sell readiness checklist

A customer opportunity is not ready for partner escalation until:

- CRM record exists;
- buyer is real;
- problem and success metric are explicit;
- Klinikos product path is available or scheduled;
- AI workload is bounded;
- data/PHI status is known;
- commercial ask is clear;
- architecture diagram exists;
- delivery owner exists;
- no unsupported product claims are required to win.

## 11. Sales deck structure for joint opportunities

Keep customer deck simple:

1. customer problem;
2. current cost/friction;
3. Klinikos operating model;
4. workflow before → after;
5. Zumi/OpenAI role;
6. authority/security boundary;
7. implementation plan;
8. measurable outcome;
9. commercial structure;
10. next step.

Do not expose proprietary internal architecture unnecessarily.

## 12. Delivery packet

Every production customer receives internally tracked:

- statement of work;
- data-flow diagram;
- environment/config register;
- acceptance tests;
- AI evaluation plan;
- rollback/degraded-mode plan;
- incident contacts;
- cost budget;
- release SHA/evidence;
- training/onboarding;
- customer signoff.

## 13. Outcome evidence standard

An outcome claim must identify:

- baseline period;
- measured metric;
- data source;
- intervention;
- comparison period;
- confounders/limitations;
- customer confirmation;
- permission level: internal, partner-confidential, public.

Avoid vague claims like `AI saved time` without evidence.

## 14. Economics

Track per joint deployment:

- implementation revenue;
- recurring revenue;
- OpenAI direct model/tool cost;
- other variable infrastructure;
- delivery labor;
- support burden;
- gross/contribution margin;
- expansion revenue;
- network value created.

Partner benefits do not excuse bad unit economics.

## 15. Red lines

Never:

- claim OpenAI endorses a customer outcome without approval;
- claim co-sell before eligibility/registration exists;
- call Partner Network acceptance a BAA;
- route PHI through an unapproved OpenAI configuration;
- let OpenAI become clinical/payment/credential authority;
- give a model unrestricted database access;
- expose customer confidential data in partner marketing;
- prioritize a partner metric over actual customer value.

## 16. 90-day partner scorecard

Track:

- Partner Portal onboarding complete;
- PartnerU admin training complete;
- current tier recorded;
- next-tier criteria recorded;
- certifications started/completed;
- co-sell/deal-registration rules captured;
- two repeatable solution patterns documented;
- at least one real customer deployment candidate;
- at least one measured OpenAI-powered workflow;
- zero unsupported partner claims;
- PHI gate status explicitly known.

## 17. North star

> **Klinikos should become valuable enough that OpenAI can help distribute it, not dependent enough that OpenAI has to make it valuable.**
