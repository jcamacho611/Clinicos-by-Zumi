## Capability routing law

Use available capabilities when they materially improve correctness, speed, evidence, security, or artifact quality. Do not invoke a tool ceremonially.

Preferred routing examples:

- GitHub — current code, branches, PRs, CI, exact-head evidence, repository writes and merges.
- Superpowers — design discipline, planning, TDD, debugging, review, branch finishing and verification.
- Stripe — live payment/billing truth when commercial claims or payment rails are in scope.
- Cloudflare / hosting provider — live edge, deployment, domain, runtime or infrastructure evidence when in scope.
- Supabase / database provider — only for the verified Klinikos environment; never cross-contaminate another product or organization.
- Browser / frontend verification — real route, viewport, keyboard, reduced-motion, accessibility and interaction proof.
- Figma / Canva / image generation / visualization — use the appropriate visual surface for product, editable design, marketing, reference imagery or architecture; generated material is never runtime evidence.
- Outlook / Gmail / Calendar / Drive — use only when the task actually requires those connected business records or actions; external communications and commitments remain authority-gated.

If a capability is unavailable, route to the strongest safe alternative rather than stopping.

## No-Blocker execution law

A blocked provider, model, plugin, API, vendor, account tier, quota, file format, SDK, browser feature, region or convenience service is a **routing problem**, not automatically a project blocker.

Default route:

`PRIMARY PATH → FALLBACK A → FALLBACK B → OPEN STANDARD / EXISTING PROVIDER → NATIVE IMPLEMENTATION → MANUAL-BUT-TRUTHFUL WORKFLOW`

Choose among fallbacks using:

- business outcome preserved;
- security/privacy preserved or improved;
- lowest responsible cost;
- implementation and maintenance burden;
- lock-in;
- strategic leverage;
- revenue/conversion impact;
- truthful operational state.

Never add unnecessary infrastructure merely to replace a convenience feature.

### AI fallback

Zumi remains provider-neutral at the orchestration boundary.

`TASK CLASSIFICATION → APPROVED MODEL/ADAPTER → DEGRADED CAPABILITY IF NEEDED → TRUTHFUL RESULT`

An AI outage never widens authority. Deterministic/server rules remain authoritative for consequential actions.

### Payment fallback

Payment providers are rails, not Klinikos business authority.

If a rail is unavailable, preserve Offer, obligation, entitlement, reconciliation and audit state. Never mark payment complete without evidence. Never silently change processor, fees, settlement behavior, liability, tax treatment or customer terms.

### Healthcare integration fallback

For labs, imaging, eligibility, payer, eRx, communications, identity, credentialing and related rails:

`APPROVED PARTNER/API → ALTERNATE APPROVED PARTNER → OPEN/STANDARD INTERFACE → MANUAL-BUT-TRUTHFUL WORKFLOW`

Never fabricate a connection.

### Deployment fallback

Investigate alternate region, instance, tier, approved provider, temporary degraded mode, or self-hosting only when justified by security, economics and maintainability.

### Business/capital fallback

A rejected lender, investor, grant, partner, buyer, procurement route or jurisdiction produces a structured reason, deficiency, adjacent route and reusable lesson. One rejection should improve future qualification.

## Mandatory stop conditions

Do not silently route around a blocker when the fallback would:

- spend or commit company funds;
- enter a contract;
- send external communications;
- accept or confirm a meeting;
- make a legal or compliance attestation;
- weaken security/privacy controls;
- expose PHI/PII or crown-jewel logic;
- materially alter approved product architecture;
- change customer commercial terms already offered;
- create regulated authority;
- fabricate evidence.

Those require the appropriate authority.

## Source recovery and anti-compression

When the founder supplies large prompt bundles, old chats, exports, research, clinician feedback, business experiments or duplicate files:

1. deduplicate exact and near-duplicate material;
2. classify each item as `CURRENT LAW`, `ACCEPTED REQUIREMENT`, `IMPLEMENTATION EVIDENCE`, `HISTORICAL`, `SUPERSEDED`, `CONFLICT`, or `PROVENANCE ONLY`;
3. preserve one-off requirements that materially affect product, business, authority, safety, economics or network effects;
4. merge accepted permanent law into the existing Master Canon only when necessary;
5. route implementation consequences into the existing Master Engineering Blueprint / Master Execution Engine / execution traceability ledger;
6. retain historical material as provenance without reviving it as current authority;
7. never create a second Master Canon merely because a source is large.

Founder omission never means product omission. Compression is allowed; erasure is not.
