## 1. Commercial objective

Klinikos should monetize the durable economic layers of the operating network without fragmenting into unrelated products and without charging for authority that money cannot legitimately create.

The commercial stack is:

`FREE NETWORK LIQUIDITY → BASE SOFTWARE → CONFIGURATION / SPECIALTY PACKS → INTELLIGENCE / AUTOMATION → CUSTOMER-FUNDED USAGE → IMPLEMENTATION / SERVICES → PERMITTED TRANSACTION INFRASTRUCTURE → ENTERPRISE / INSTITUTIONAL / API / PRIVATE DEPLOYMENT`.

Permanent rule:

> Charge for operating leverage, automation, intelligence, fulfillment infrastructure, configuration, service delivery, and permitted economic execution. Do not charge for the identity/trust/network behavior Klinikos needs more of, and never sell regulated authority.

## 2. Five Stripe treatments

Every commercial object must resolve to one of:

1. `PUBLIC_SELF_SERVE` — standardized purchase; server-owned price; automatic Stripe collection; signed evidence before bounded fulfillment.
2. `PUBLIC_SUBSCRIBE` — standardized recurring software/membership; automatic Billing collection after entitlement lifecycle exists.
3. `PRIVATE_QUOTED` — price or scope depends on qualification, contract, configuration, risk, integration, location, volume, institutional terms, or regulated context. Stripe may still collect automatically once the governed quote/contract is approved.
4. `PREPAID_USAGE` — bounded customer-funded variable-cost balance. Reuse the provider-neutral Financial OS ledger; never create a Stripe-specific wallet as source of truth.
5. `NOT_DIRECTLY_PURCHASABLE` — authority/truth that payment can never create.

`automatic payment collection` is separate from `automatic authority`. Stripe should collect automatically when the commercial route reaches payment. Klinikos deterministic policy decides what purchased software/service entitlement may happen afterward.

## 5. Packaging law — prevent SKU explosion and double charging

A broad Stripe catalog is useful only if packaging remains simple to the buyer.

The public experience should generally show:

- Free Person / basic Grid / basic EDU;
- Professional Pro or Business when relevant;
- Core / Growth / Scale for clinics;
- a small number of outcome-oriented add-ons;
- Enterprise/custom when complexity requires it.

The Offer Registry must compute package composition.

Examples:

- if Growth already includes a capability, do not bill the standalone add-on again;
- if Scale includes expanded intelligence, charge only incremental/private-intelligence scope;
- if an Enterprise contract contains Network or Quality operations, the corresponding standalone Stripe price becomes `included`, not an additional charge;
- a Specialty Pack configures shared Klinikos; it does not create a separate application;
- customer-funded external usage remains separately metered even when the capability is included.

## 8. Stripe capability architecture

### Standardized purchases

Use Stripe-hosted Checkout or Payment Links for high-conversion automatic payment collection. Payment Link metadata must remain non-PHI and non-secret.

### Recurring software

Use Stripe Billing with stable lookup keys and pricing versions. Customer Portal is the preferred self-service lifecycle surface once plan-change rules are implemented. Smart Retries and automated payment recovery should be enabled for recurring billing.

### Sales-led B2B / enterprise

Use Stripe Quotes + Invoicing. Complex scope should never be forced into a public Buy Now price. Approved invoices may use automatic collection or hosted invoice/ACH depending on contract terms.

### Usage

Use included allowance → prepaid provider-neutral usage balance → explicitly bounded overage if authorized → stop/degrade safely. Never treat a saved card as unlimited spend authority.

### Connect

Maintain two separate rails:

1. `SAAS MERCHANT PAYMENTS` for a clinic/business accepting payment from its own customer;
2. `GRID MARKETPLACE PAYMENTS` only for approved resource classes and policy states.

Do not let one Connect implementation silently decide the merchant-of-record, liability, fee-splitting, or payout model for every healthcare transaction.

### Tax

Begin with Stripe Tax threshold monitoring. Collect tax only after registrations/obligations are verified. Product tax classification must be reviewed before live activation.
