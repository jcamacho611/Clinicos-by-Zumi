## 2. Commercial decision rule for every new Universe concept

Before creating a product/price/link, classify the concept:

### A. `NEW ECONOMIC SURFACE`
Use only when the concept creates distinct buyer value, distinct cost-to-serve, distinct entitlement/delivery, and a clear upsell/contract boundary.

### B. `PACKAGE / ADD-ON VARIANT`
Use when the capability materially increases value but belongs inside an existing product family.

### C. `INCLUDED INFRASTRUCTURE`
Use when charging separately would weaken trust, safety, continuity, UX, or product coherence.

### D. `TRANSACTION POLICY`
Use when economics depend on resource class, buyer/seller class, jurisdiction, merchant structure, fulfillment, dispute model, or Connect configuration.

### E. `CUSTOM ENTERPRISE / INSTITUTIONAL`
Use when scope varies too much for a safe public fixed price.

### F. `NOT MONETIZABLE AUTHORITY`
Use when payment must never create the truth or permission.

This is the anti-SKU-sprawl law.

## 3. New Living Universe concepts — monetization disposition

### 3.1 Care Circle

**Disposition: `INCLUDED INFRASTRUCTURE`**

Do not create a Care Circle subscription merely because the relationship model is valuable.

Reason:
- caregiver/guardian/proxy authority is a governed relationship, not a product entitlement;
- charging for basic patient-adjacent relationship access would create bad consumer optics and network friction;
- the feature increases retention/value of Patient, Clinic OS, and enterprise deployments.

Potential premium value can exist later around convenience/concierge tooling, but never around buying authority to another person's health information.

### 3.2 Handoff Receipts

**Disposition: `INCLUDED INFRASTRUCTURE / PACKAGE VALUE`**

`CREATED → SENT → RECEIVED → ACKNOWLEDGED → ACCEPTED → OWNED → COMPLETED`

Handoff Receipts should increase the value of:
- Network;
- Referral workflows;
- Orders/results;
- Placement OS;
- Grid fulfillment;
- Quality & Compliance;
- enterprise implementation.

Do not create “Handoff Receipt Pro.” Continuity evidence is part of why the higher-level products are worth paying for.

### 3.3 Operational Digital Twin

**Disposition: `SCENARIO / ENTERPRISE SERVICE + RECURRING ADD-ON CANDIDATE`**

Commercial thesis:
- sell the initial modeling/design engagement through Enterprise Architecture Workshop / implementation services;
- recurring value may later justify a private simulation/modeling subscription.

Current sandbox scenario anchors created for exploration:
- **$5,000 starting setup**;
- **$1,500/month** recurring scenario.

These are not approved public prices.

Potential buyers:
- multi-location organizations;
- health systems;
- workforce/education institutions;
- clinics opening new locations;
- enterprise implementation customers.

Potential value:
- staffing scenarios;
- scheduling/capacity modeling;
- new-location planning;
- workflow simulation;
- synthetic implementation testing;
- EDU simulation convergence.

Never represent synthetic simulation as real patient or production truth.

### 3.4 Network Capacity Pulse

**Disposition: `SCENARIO / PACKAGE INTO NETWORK + EXECUTIVE INTELLIGENCE / ENTERPRISE`**

Current sandbox scenario anchor:
- **$2,500/month**.

Preferred packaging:

Potential value:

This must be privacy-safe and aggregation/de-identification policy must be independently approved before cross-organization intelligence is exposed.

### 3.5 Continuity Mode

**Disposition: `SCENARIO / ENTERPRISE RESILIENCE ADD-ON`**

Do not imply that Klinikos can guarantee third-party availability.

### 3.6 Network Relationship Memory

**Disposition: `INCLUDED INFRASTRUCTURE / NETWORK + ENTERPRISE VALUE`**

Do not sell memory of a relationship as a separate SKU. Use it to improve continuity, discovery, account intelligence, and retention inside Network, Grid, enterprise, and implementation surfaces.

### 3.7 Explainable Action Provenance

**Disposition: `INCLUDED SAFETY / TRUST INFRASTRUCTURE`**

Do not paywall:

- relevant rule/explanation;
- missing evidence;
- confidence/recency where applicable.

Explanation of consequential state is part of trustworthy software, not an upsell.

### 3.8 Organization Success Graph / Outcome Ledger

**Disposition: `PACKAGE VALUE`**

`BASELINE → INTERVENTION → EVIDENCE → OUTCOME → ECONOMIC VALUE`

Use it to increase:

Do not charge for an “ROI dashboard” that manufactures ROI. Only verified evidence may populate outcome/economic claims.

**Commercial treatment:** existing Clinic/Enterprise + Network/Grid + specialty configuration + customer-funded usage + integrations.

Do not create a second Klinikos codebase. If home-service-specific economics later emerge, price the configuration/workflow or institutional contract, not a new product universe.

### 4.2 Lab / imaging / diagnostics

**Commercial treatment:** Partner OS / Network / Integration / Enterprise + permitted capacity transaction policy.

Potential transaction economics belong to the diagnostic-capacity resource class, not a global Grid fee.

### 4.3 Vendor / supplier

**Commercial treatment:** Partner OS + API/Integration + permitted procurement/transaction economics.

Regulated products must remain separate from ordinary commerce policy.

### 4.4 Payer / insurance organization

**Commercial treatment:** Enterprise/custom + integration/Financial OS/Network contracts.

Do not create a public payer checkout. Payer contracts depend on data rights, network/policy scope, integration, security, and institutional terms.

### 4.5 Research / clinical innovation

**Commercial treatment:** custom institutional/enterprise contract.

Potential value:
- site operations;
- synthetic simulation;
- workflow/evidence coordination;
- approved research integrations;
- study operations.

No public patient recruitment marketplace and no research-participant exposure without governance.

### 4.6 Strategic / API partner

**Commercial treatment:** reuse existing `Klinikos API & Network Access` and integration/enterprise offer families.

Do not create a second API partner SKU.

### 4.7 Investor / lender

**Commercial treatment:** no Stripe product.

Controlled diligence and capital transactions are company-finance workflows, not customer software purchases.

### 4.8 Klinikos internal operator

**Commercial treatment:** no product charge.

Internal company tools may manage implementation, support, security, release state, opportunity pipeline, procurement, and evidence, but internal authority remains separate from customer clinical/business authority.

## 6. Stripe rails — final commercial partition

### Rail 1 — Klinikos own revenue

Checkout / Billing / Payment Links / Quotes / Invoices for Klinikos software, services, implementation, education, usage, and enterprise contracts.

### Rail 2 — merchant/customer payments

Stripe Connect SaaS/direct-charge model where an approved clinic/business accepts payment from its own customer.

This is a separate payment infrastructure product family (`Klinikos Payments`).

### Rail 3 — Grid marketplace payments

Destination charges or separate charges/transfers only for policy-approved resource classes.

One buyer payment may eventually support multiple lawful obligations, but the system must preserve merchant/seller/recipient identity, responsibility, refund/dispute model, and fulfillment truth.

### Rail 4 — enterprise/government quote-to-cash

Quotes + Invoicing / ACH / hosted invoice where contract/procurement permits.

### Rail 5 — prepaid variable usage

Reuse provider-neutral Financial OS allowance/reservation/usage/reconciliation machinery. Stripe funds the balance; Stripe does not become the ledger.

## 7. Automatic payment law

Founder direction is explicit: approved offers should collect automatically where the commercial route reaches payment.

Correct model:

`QUALIFIED / SELF-SERVE OFFER → SERVER-OWNED PRICE → STRIPE CHECKOUT/BILLING/INVOICE → AUTOMATIC COLLECTION → SIGNED PROCESSOR EVIDENCE → KLINIKOS FINANCIAL OS → BOUNDED ENTITLEMENT / DELIVERY`

Human review should not be inserted merely to “approve that Stripe may charge” when the offer and buyer are already eligible.

But automatic collection does not mean automatic regulated authority:

`PAYMENT != PHI ACCESS`
`PAYMENT != CREDENTIAL`
`PAYMENT != CLINICAL AUTHORITY`
`PAYMENT != GRID HARD ELIGIBILITY`
`PAYMENT != IMPLEMENTATION COMPLETE`

## 12. Council recommendation

Do not optimize Stripe for the largest number of products.

Optimize for:

`FREE LIQUIDITY → FIRST PAID VALUE → RECURRING OPERATING VALUE → ADD-ON / USAGE EXPANSION → TRANSACTION INFRASTRUCTURE → INSTITUTIONAL / ENTERPRISE VALUE → NETWORK EFFECT`
