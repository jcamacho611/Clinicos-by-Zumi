# KLINIKOS — MAXIMUM CINEMATIC PRODUCT REALIZATION SCOPE

Status: AUTHORITATIVE EXECUTION DIRECTIVE  
Date: 2026-08-14

This document expands the approved cinematic rose direction to the maximum coherent product scope. It does not authorize fake capability, invented data, weakened security, or uncontrolled regulated workflows. It defines the target product experience that implementation should converge toward.

## 1. Product-wide objective

The cinematic Living Home is not a theme applied to one page. It becomes the interaction and presentation grammar for Klinikos across public discovery, authentication, activation, Clinic OS, Grid, Care, EDU, Intelligence, patient experiences, commercial flows, and authorized administration.

The product should feel like one living operating environment that forms around user intent.

## 2. Universal shell

Build one adaptive Klinikos shell with:

- compact brand identity;
- role-aware global navigation;
- command/composer access where appropriate;
- truthful intelligence state;
- contextual notifications/attention;
- profile/organization switching where authorized;
- progressive disclosure rather than permanent module clutter;
- responsive desktop/tablet/mobile behavior;
- keyboard navigation, focus management, reduced-motion support and accessible contrast.

The shell changes density and emphasis by context. Public, patient and operational users must not see inappropriate controls merely because they share the same design system.

## 3. Living Home as orchestration surface

Expand Living Home from conversational landing page into an adaptive work surface capable of rendering structured workspace blocks inside the same continuous context.

Supported workspace families should include, as repository capability allows:

- priorities and attention queue;
- patient lookup and patient operations;
- appointment/scheduling context;
- forms/documents/follow-up;
- staff/team work;
- revenue opportunities and billing readiness;
- Grid demand/supply/matches/bookings;
- Care workflow;
- EDU discovery/progress;
- operational insights;
- activation/setup status;
- authorized research/intelligence results.

A request should preserve its conversational context while exposing the useful controls and data needed to act.

## 4. Intelligence interaction model

Use a truthful visible state model:

IDLE/LISTENING → UNDERSTANDING → PREPARING → CONNECTING when real retrieval/tool work occurs → READY when a useful result/workspace is actually available.

Also support WAITING_FOR_CONFIRMATION, BLOCKED, ERROR, PARTIAL and PENDING_EXTERNAL states.

Intelligence can interpret, retrieve authorized context, summarize, plan, compare, calculate, research permitted public information, prepare actions and coordinate workflows. Deterministic systems remain authoritative for auth, permissions, eligibility, credentials, payment, transaction state, clinical release and safety.

## 5. Clinic OS realization

Convert existing clinic operations into the same visual/interaction grammar and connect them to Living Home.

Priority domains:

- patients and registry/search;
- intake/forms/documents;
- appointments/calendar;
- staff tasks and workflow;
- follow-up;
- referral/result tracking where implemented;
- clinician/visit workflow where legitimately supported;
- owner/operator overview;
- revenue leakage/readiness;
- reporting/insights based on legitimate data;
- multi-location context when authorized and supported.

Replace dashboard sprawl with task-first surfaces. Existing useful screens may remain as deep workspaces but should be reachable from intent and context.

## 6. Grid realization

Grid becomes a cinematic but highly functional healthcare resource orchestration network.

The simplest universal expression remains:

- I NEED
- I HAVE

Support current legitimate Grid capability first and evolve toward generalized participants, resources, demand, requirements, availability, eligibility, matches, offers, bookings/reservations, fulfillment, financial state, disputes/incidents and reputation/evidence.

The UI should support:

- map/list discovery;
- explicit location permission;
- privacy-reduced public coordinates;
- exact server-side eligibility calculations;
- saved demand;
- filters;
- availability;
- match explanation;
- verification state;
- offer/acceptance;
- booking state;
- fulfillment state;
- truthful empty markets;
- earnings/financial state where supported;
- credential/trust state;
- organization/facility capacity.

Long-term resource classes include work, providers, space, services, permitted equipment/resources, education capacity, referral/care capacity and business services. Policy is resource-class specific.

## 7. Care realization

Care is a governed patient/care workflow, not a generic AI diagnosis screen.

The cinematic direction should support authorized experiences such as:

- patient context;
- appointments;
- forms;
- follow-up;
- referrals/results;
- care-related tasks;
- provider review states;
- communication preparation;
- clear human/clinical responsibility.

Do not imply clinical decisions, prescriptions, orders, insurance authorization or external delivery that the system has not legitimately completed.

## 8. EDU realization

EDU is first-class in global product identity.

Build a focused educational environment using the same visual grammar for:

- learning discovery;
- courses/modules where implemented;
- progress;
- competency/evidence;
- training opportunities;
- future Grid-linked placement/preceptor capacity.

EDU should feel like Klinikos, not an embedded generic LMS.

## 9. Patient experience

Patient-facing Klinikos should be dramatically simpler than staff Klinikos.

Prioritize:

- what is next;
- appointments;
- forms/documents;
- balances/payment state where supported;
- messages/communications where supported;
- referrals/follow-up where supported;
- simple care navigation.

Never expose clinic administration, internal Grid data, backend terminology or organization-wide operational intelligence.

## 10. Revenue and billing realization

Create a truthful revenue workspace from available data rather than a decorative finance dashboard.

Potential supported concepts:

- revenue opportunities;
- incomplete operational steps affecting revenue;
- billing readiness;
- balances/payment evidence where implemented;
- recovered/at-risk workflow value only when legitimately derived;
- commercial subscription/entitlement state.

Do not claim claims submission, eligibility, denial resolution, payout, settlement or recovered revenue unless evidence supports it.

## 11. Insights realization

Insights should answer operational questions, not display arbitrary charts.

Examples:

- what changed;
- what needs attention;
- where work is accumulating;
- what capacity is unused;
- where follow-up is incomplete;
- which legitimate revenue opportunities exist;
- Grid supply/demand health;
- activation/setup blockers.

Every number needs provenance from real/demo-explicit data.

## 12. Public commercial experience

Extend the cinematic system to public surfaces without turning them into the authenticated operating UI.

Public pages should clearly communicate:

- what Klinikos is;
- who it helps;
- Clinic OS;
- Grid;
- EDU;
- Klinikos Intelligence;
- operational audit/analysis;
- implementation;
- subscription/activation;
- truthful availability and pending connections.

Commercial flow should connect discovery → offer → server-owned checkout intent/evidence → activation → first login → Living Home.

## 13. Activation and onboarding

After legitimate payment/entitlement, onboarding should feel like the product coming alive rather than a long settings wizard.

Progressively gather only what is needed for:

- organization identity;
- role;
- team invites;
- location;
- desired workflows;
- external connections;
- Grid participation;
- first useful operational objective.

Finish by delivering a useful Living Home state, not a congratulations dead end.

## 14. Design-system expansion

Canonical converted palette:

- obsidian/near-black foundation;
- black cherry/deep oxblood structural surfaces;
- warm ivory primary text;
- dusty rose/muted coral/ember pink emphasis;
- rose-gray separators/borders;
- semantic colors only when status meaning requires them.

Systemize:

- typography scale;
- spacing rhythm;
- borders;
- radii;
- shadows/glows;
- motion duration/easing;
- state transitions;
- data density;
- focus/hover/pressed/disabled states;
- empty/error/loading/skeleton states;
- responsive breakpoints.

Motion must communicate state, hierarchy or continuity. Avoid ornamental animation that competes with work.

## 15. Signature rose behavior

Treat the rose as an intelligence/environment motif with controlled variants:

- public hero/brand expression;
- Living Home idle focal state;
- receded active-work state;
- subtle transition/state texture;
- never a generic background pasted behind every page.

Do not reduce readability or performance for the rose.

## 16. Navigation and information architecture

Top-level user-facing destinations are governed by role but conceptually include:

- Dashboards / Home
- Grid
- Care
- EDU
- Intelligence

Contextual operational actions include:

- Patients
- Grid
- Care
- Billing/Revenue
- Insights

Do not expose destinations users cannot access. Do not create dead navigation. Deep existing routes can remain but should be organized under this understandable hierarchy.

## 17. Command-first product behavior

Natural language becomes a universal shortcut into the product, not a replacement for deterministic controls.

Examples:

- “What needs my attention today?”
- “Find the patients who still need forms.”
- “I need an RN Friday.”
- “I have a treatment room open Tuesday.”
- “Show me where we're losing follow-up.”
- “Find training for this.”

Interpret intent, retrieve authorized data, render a structured result/workspace, and preserve direct UI controls for verification/action.

## 18. Data and state truth

Every surface must distinguish:

- real production data;
- explicit demo/sandbox data;
- calculated data;
- pending external state;
- manual fallback;
- unavailable capability.

Never use fabricated values to make the product appear busy.

## 19. Security and privacy

The redesign must preserve or strengthen:

- tenant isolation;
- RBAC/resource authorization;
- minimum necessary access;
- audit trails;
- credential/eligibility rules;
- payment evidence;
- patient data controls;
- redaction before unrestricted external AI/tools/web;
- explicit geolocation permission;
- public coordinate privacy reduction;
- safe error handling.

Treat tests as adversarial attempts to cross boundaries.

## 20. External integrations

Represent external capability through explicit states such as READY, CONFIGURED, MANUAL_FALLBACK, ADAPTER_READY, PENDING_CONNECTION, EXTERNAL_APPROVAL_REQUIRED and BLOCKED.

A connected-looking UI is not proof of a live integration.

## 21. Performance

Cinematic does not mean slow.

Target:

- fast first meaningful paint;
- responsive composer/input;
- progressive loading of heavy visuals;
- lazy/deferred secondary content;
- no blocking decorative media;
- stable layout;
- optimized assets;
- graceful low-power/reduced-motion behavior.

## 22. Testing matrix

Before declaring realization complete, test:

- public desktop/mobile;
- login/auth;
- activation;
- role routing;
- Living Home idle and active states;
- unknown conversational request;
- patient lookup/workspace;
- operational priorities;
- revenue workspace;
- Grid I NEED/I HAVE;
- geolocation permission and denial;
- Grid empty market;
- Grid eligible/ineligible paths;
- Care authorized/unauthorized paths;
- EDU routing;
- intelligence errors/pending external state;
- tenant isolation;
- keyboard navigation;
- reduced motion;
- production build/start/health.

## 23. Reference fidelity loop

For reference-locked surfaces:

1. render exact target viewport;
2. capture screenshot;
3. compare against approved reference;
4. correct geometry, typography, scale, crop, density, color, contrast, glow and rhythm;
5. repeat until discrepancies are minor and intentional only for real product truth/accessibility/responsiveness.

## 24. Implementation priority

Execute in this order unless current repository evidence dictates a safer dependency order:

1. shared design tokens/primitives;
2. universal shell/header/navigation;
3. Living Home reference fidelity;
4. composer and truthful intelligence state machine;
5. same-surface workspace renderer;
6. operational priority/revenue/team/Grid cards from real data;
7. Patients/Grid/Care/Billing/Insights rails;
8. Clinic OS deep surfaces conversion;
9. Grid end-to-end conversion and wiring;
10. Care conversion;
11. EDU conversion;
12. patient experience conversion;
13. public/commercial conversion;
14. activation/onboarding conversion;
15. responsive/accessibility/performance hardening;
16. visual regression and journey coverage;
17. production verification.

## 25. Completion law

Do not call the vision complete because tokens changed or Living Home looks impressive.

Complete means the approved visual grammar has become a coherent product system, major visible controls are real, user intent can bring forward useful authorized work, data is truthful, critical journeys work, security remains intact, mobile is intentional, and production gates pass.

North star:

**Klinikos should feel like an intelligent healthcare environment constructing the correct workspace around the user while hiding enormous backend complexity underneath.**
