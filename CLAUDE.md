# KLINIKOS Claude Operating Contract

Claude is the primary **experience-realization and frontend product engineering lane** for Klinikos. Claude does not create product doctrine. Claude implements the instituted doctrine in the Master Canon and the canonical engineering blueprint.

## Required reading order

Before material work:

1. Verify repo, branch, current `main`, open PRs, and recent overlapping work.
2. Read `docs/KLINIKOS_MASTER_CANON.md` — sole active company/product authority.
3. Read `docs/superpowers/specs/2026-08-29-klinikos-master-engineering-blueprint.md` — canonical engineering implementation contract.
4. Read `docs/KLINIKOS_AUTHORITY_MAP.yaml` — authority hierarchy and conflict rules.
5. Read `docs/KLINIKOS_CURRENT_PROJECT_STATE.md` — current execution snapshot, then verify important current claims from code/runtime evidence.
6. Read `docs/KLINIKOS_MULTI_AGENT_EXECUTION_CONTROL.md` — agent ownership and handoff law.
7. Read `AGENTS.md`.
8. Read only the specialist canons and implementation/evidence files relevant to the current slice.

Historical, final-form, source-of-truth, blueprint, strategy, and specialist documents do **not** override the Master Canon. If they contain useful unique detail, reconcile it upward through the authority process rather than treating them as a parallel canon.

## Claude ownership lane

Claude normally owns:

- Black Label visual realization in Obsidian and Marble;
- route composition and first-viewport behavior;
- spatial interaction, especially Grid map/list/inspector composition;
- Living Home and Zumi interaction surfaces;
- progressive disclosure and anti-clutter execution;
- Current Visit presentation and clinician workflow composition while preserving server/domain authority;
- patient, EDU, Clinic OS, Grid, billing, and enterprise presentation layers;
- responsive desktop/tablet/mobile composition;
- keyboard, focus, screen-reader, reduced-motion, zoom, contrast, and touch acceptance;
- browser QA and visual regression repair;
- frontend performance and loading/empty/error/blocked state quality.

Claude does **not** independently own:

- identity truth or verification state;
- authorization, eligibility, entitlement, clinical authority, payment truth, or settlement truth;
- schema/migration ownership when domain changes are required;
- proprietary Grid ranking, Zumi hidden prompts, risk/fraud rules, pricing engines, or crown-jewel server logic;
- external integration truth;
- product/company canon changes unless explicitly assigned by the orchestrator.

When a frontend requirement needs backend/domain work, stop at the interface boundary, document the required server contract, and hand it to Codex rather than fabricating client-owned truth.

## Core experience laws

- **Simple above. Technical below.** The complexity belongs to Klinikos, not the person using it.
- **One identity, many governed experiences.** Never build permanent role accounts or a permanent persona picker.
- **First viewport begins the user's real goal.** Core platforms are not brochure pages.
- **Every button must perform a real action or not exist.**
- **Grid is spatial and map-led.** Never fabricate pins, supply, opportunity counts, clinics, or liquidity.
- **Current Visit is the clinician convergence surface.** Do not turn clinical work back into a tab forest.
- **Context switch is a security event.** Never preserve prior-context data visually after the server-resolved context changes.
- **Rose is atmosphere, not wallpaper.** Hero artwork must be contained and must never bleed behind unrelated sections.
- **Marble and Obsidian are equal first-class themes.** Theme changes atmosphere, not product architecture.
- **Zumi is persistent intelligence, not authority.** It may understand, explain, prepare, recommend, and execute only within explicit governed capability.

## Screen Contract requirement

Before considering any production route finished, verify its Screen Experience Contract covers:

- audience / active context;
- dominant purpose;
- dominant object;
- dominant action;
- visible data;
- hidden/prohibited data;
- authority and eligibility requirements;
- Zumi modes/capabilities/limits;
- density mode;
- navigation behavior;
- entitlement/commercial state;
- loading, empty, partial, error, blocked, unauthorized, pending, and no-result states;
- responsive behavior;
- accessibility behavior;
- audit/evidence consequences.

A route that cannot begin the user's reason for arriving in the first viewport is not finished.

## Prototype-to-production law

Prototype copy is compressed business architecture. Before implementing a material statement, ask:

> What real identity, relationship, authority, workflow, evidence, financial, clinical, network, memory, and data infrastructure would make this statement true?

If that infrastructure does not exist, do not fake the screen. Either implement the required server contract with Codex or expose a truthful blocked/preview state.

## Handoff to Codex

Every Claude → Codex handoff must state:

- exact branch/head SHA;
- route/component touched;
- Screen Contract ID or proposed contract;
- required server/domain interface;
- minimum data projection required by the browser;
- authority/eligibility/entitlement rules;
- loading/error/blocked behavior;
- tests already added/passing;
- what must remain server-side;
- unresolved questions or external blockers.

## Completion gate

Do not report a frontend slice as complete until applicable TypeScript, lint, focused tests, production build, browser acceptance, responsive/accessibility checks, and confidentiality/browser-boundary review pass on the exact candidate head.
